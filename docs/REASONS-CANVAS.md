# REASONS Canvas — plan-mcp (v2: blueprint / architectural-standard)

> Structured Prompt-Driven Development canvas. See vault note `Coding/AI/Reasons-Canvas-SPDD.md` for the method. This canvas is the source of truth — if implementation and this document diverge, fix this document first, then regenerate/update code.
>
> **This is v2.** v1 (a minimal SVG plan renderer on Turf.js) is implemented and committed, but is **superseded** by this canvas: the goal is now output that reads as a real architectural drawing — blueprint aesthetic, real units + named scale, professional line-weight hierarchy, poché/material hatching, dimensioning, structural grid, title block, north arrow and scale bar. This requires a different geometry engine and a substantially rebuilt renderer. Operations below are written as a from-scratch rebuild; v1 pieces that survive unchanged are called out where relevant (MCP scaffold, output-path sandboxing, XML-escaping).

## R — Requirements

Build an MCP server, usable by **any** MCP-capable LLM client (primarily CLI coding agents like Claude Code, not a human typing coordinates by hand), that renders 2D plan-view architectural drawings as SVG from a **structured JSON description**, in a **blueprint aesthetic that follows architectural drawing conventions**, at two scales:

1. **Site scale** (`render_site_plan`): an exterior site plan spanning urban figure-ground down to a **detailed residential plot** — buildings (poché footprints), parcels/lot lines, roads, **hardscape (sidewalks/driveways/parking/patios/porches/decks), water features (pools/ponds), soft landscape (lawns/gardens/backyards), barriers (fences/walls/hedges/gates), and trees**. The architectural term is "site plan"; this replaces v1's `render_city_map`.
2. **Building scale** (`render_floor_plan`): the interior floor plan of a single building — one or more floors, each with rooms, walls (cut, with poché/material hatch), door/window openings, dimensions, and an optional structural grid. A single-floor house or a multi-floor building (each floor its own sheet).

What "reads as a real architectural drawing" means here, concretely (all in scope for v1 of this canvas — the user selected the full apparatus):

- **Blueprint aesthetic**, theme-driven: default `blueprint` (deep Prussian-blue ground, white / pale-cyan linework — the cyanotype tradition), plus an opt-in `whiteprint` theme (black-on-white, the modern construction-document look).
- **Per-element color fill override**: any drawable element may declare a `fill` in the spec to be filled with a specific color, so individual elements (a highlighted room, a subject building) stand out against the otherwise monochrome linework. This is a first-class feature, not just styling sugar.
- **Real units + named scale + scale bar**: the spec declares a real `unit` (`mm`/`cm`/`m`/`ft`/`in`) and a paper `scale` (e.g. `1:100`). Dimensions read in real units; the sheet shows the named scale and a graphic scale bar calibrated to it. Line weights and text heights are authored in **paper-mm** and converted to model units via the scale (so a 1:50 plan and a 1:1000 site plan both read correctly).
- **Door swing (render form)**: a door is drawn as a **single leaf line** from the hinge to the fully-open leaf tip (perpendicular to the wall on the `swingSide`) plus a **quarter-circle arc** of radius = leaf length swept from the closed jamb (along the wall) to that open tip. The hinge is the arc's pivot but is **not** itself a vertex on the drawn arc polyline (drawing hinge→closed-jamb as a straight radius would add a spurious segment and stop the symbol reading as a clean 90° swing). Leaf ⟂ wall = the right angle a door swing must show.
- **Site figure-ground fill**: on a site plan, a building footprint uses a dedicated `buildingFill` — denser/darker than the interior wall poché — so the building mass stands clearly against a busy ground of surfaces and landscape.
- **Barrier line symbols**: a barrier is not a plain thin line — each `barrierType` gets a distinct symbol so it reads at a glance: **fence** = medium line with periodic tick posts; **wall** = heavy solid line; **hedge** = dashed line; **gate** = light broken line.
- **Line-weight hierarchy** (ISO-128-style, ~4–5 weights): heavy (cut walls / building outline) → medium (frames, secondary cut) → light (surfaces, fixtures) → fine (dimensions, hatching, grid, annotation). Plus **line types**: solid (visible/cut), dashed (hidden/above), dash-dot (centerlines, structural grid, property line).
- **Poché & material hatching**: cut walls and figure-ground buildings are filled — solid poché by default, or a standard 45°/material **hatch pattern** (concrete, brick, masonry, insulation, earth, …) when a material is given.
- **Dimension strings**: chained dimension lines with 45° architectural ticks, offset extension/witness lines, real-unit text above the line.
- **Structural grid**: dash-dot column grid with lettered/numbered circle bubbles (A/B/C, 1/2/3), optional per spec.
- **Sheet furniture**: a sheet border + title block (drawing title, scale, date, drawing number, project), a **north arrow**, and a **graphic scale bar**.

Definition of done:
- Server runs over stdio, discoverable as a standard MCP server; exposes `render_site_plan` and `render_floor_plan`; both output SVG (MCP content; optional file write). Deterministic: identical spec → byte-identical SVG.
- Neither tool does any LLM inference internally — the calling LLM produces the structured spec; the server turns valid structured input into a correct, standards-compliant SVG.
- Worked example A — **residential plot plan**: a house footprint (poché) on a parcel with lot lines, plus its grounds — driveway + sidewalk (hardscape), a pool (water), lawn + garden beds (soft landscape), a fence (barrier), and trees, with north arrow, scale bar, title block; blueprint theme. (Demonstrates the full outdoor entity set; an urban figure-ground is the same entities at larger scale.)
- Worked example B — **house floor plan**: rooms, walls with material poché, doors + windows, a full dimension string, one room highlighted via `fill`, title block + scale bar.
- Worked example C — **two-floor building**: two per-floor sheets, with a structural grid and column bubbles.
- Worked example D — **theme + fill**: the same house rendered in `whiteprint`, demonstrating theme switching and the per-element fill override.

Out of scope for v1 of this canvas (explicitly deferred): 3D/isometric/axonometric and any projection (plan view only — no sections/elevations); raster export (PNG); **DXF/DWG export** (a legitimate future "editable in CAD" feature, but SVG is the right format for a rendered blueprint and stays the sole output for now); real geodata import (GeoJSON/lat-lon); furniture/fixture/appliance and stair symbol libraries (walls/openings/rooms/dims/grid only — a stair is a deferred symbol); MEP/electrical/plumbing symbols; **automatic** dimensioning or auto-grid inference (dimensions and grid lines are spec-driven — the LLM supplies them, the server renders them correctly); **fixed real-paper-size sheet layout** (A1/A3 etc. — v1 sheets are proportional to content, not snapped to a paper size, see Approach); and code-compliance/structural validation.

### Contract for callers (this MCP is driven by an LLM, not a human)

**The server renders exactly what the spec describes; it does not infer, correct, or complete the design.** Geometric coherence — and any *intentional* incoherence — is the **caller's responsibility**. The caller (the LLM producing the spec) must ensure the plan makes sense before calling the tool:
- **Rooms tile the floor.** Room polygons should partition the interior without overlaps or unintended gaps; each is authored to the interior wall face. The server does not derive rooms from walls or walls from rooms — you place both, consistently.
- **Walls enclose.** Wall centerlines must actually meet/overlap at corners to form closed enclosures (they are unioned, so overlapping endpoints merge cleanly). A wall that stops short of the next wall leaves a gap the server will faithfully render.
- **Openings connect.** A door should sit on the wall segment that actually separates the two spaces it joins, and `positionAlongWall` should place it where those spaces are adjacent. The server cuts the opening wherever you point it — including into the wrong room or into solid poché if the spec is wrong.
- **Circulation is reachable.** Every room a person should reach must be reachable from an entrance through a connected sequence of doors. The server does **no** wayfinding/reachability check: "bedroom only reachable through another bedroom," "a room with no door," or "a bathroom with three walls" are all valid *input* the server will render as given. If that layout is intended (walk-through closet, open-plan with no divider, mechanical chase), it renders fine; if it is a mistake, it is a mistake in the spec, not the render.

Rationale: the renderer is deliberately a pure function from a valid structured spec to a correct SVG (see the Definition-of-done "no LLM inference" line). Adding architectural judgment to the server would blur that boundary and would wrongly reject legitimate unconventional plans. The caller owns semantics; the server owns faithful, standards-compliant drawing.

### Capability boundary (what the plan model can and cannot represent)

The floor plan is a **2D horizontal cut at a fixed height** with a walls + rooms + openings vocabulary. It has **no vertical dimension** and **no fixture/structure vocabulary beyond walls**. Consequently, as of this canvas:
- **Walls are full-height only.** There is no wall height, so **half-walls / low walls / partial-height partitions / railings** cannot be distinguished from a full wall — they would render as ordinary solid poché. (Deferred: a `heightClass`/below-cut flag rendering a dashed or lighter outline.)
- **No isolated masonry / columns / piers** as a first-class entity (only grid *bubbles* exist, not the column). No **curved or arched** walls — walls are straight polyline segments. No **stairs/ladders** (deferred symbol, as above).
- **Per-wall `material` renders per material group.** Walls are grouped by `material`, and each group is offset+unioned+opening-cut+hatched independently. Junctions *within* one material stay seamless (single union); a seam *between* two different materials is intentional and correct — it is the material-change line. So a brick exterior + concrete interior on one floor renders each with its own hatch. (Earlier this collapsed the whole floor to `walls[0]`'s material; that is fixed.)

These are honest boundaries a caller should design within (or route around by choosing the closest supported representation).

## E — Entities

Coordinates are 2D `[x, y]` in the spec's declared real `unit`, SVG-native axes (origin top-left, +x right, +y **down**), 1:1 into SVG user space (no y-flip). Every drawable entity accepts an optional **`style`** override; unset fields fall back to type + theme defaults.

### Shared
- **DocumentMeta** (on every root spec): `unit` (`mm`|`cm`|`m`|`ft`|`in`), `scale` (`"1:N"`), `theme` (`blueprint` default | `whiteprint`), and `titleBlock` (`title`, `drawingNumber`, `date`, `project`, `northAngle` in degrees — 0 = north-up) — all optional except `unit` and `scale`.
- **Style** (per-element override): `fill` (a **safe color token** — `#rgb`/`#rrggbb` or a named-color allowlist — this is the per-element highlight feature), `stroke` (same token set), `lineweight` (role name: `heavy`|`medium`|`light`|`fine`), `linetype` (`solid`|`dashed`|`dashdot`), `hatch` (material name → pattern, or `solid`/`none`). All optional; the renderer resolves unset fields from the entity type's role + the theme.
- **Label**: `text`, `position` (`[x,y]`) or `anchorEntityId` (auto-place at the entity centroid), `heightMm` (paper-mm text height, default per role), optional `tag` (draw a room-tag box around it). Text is always XML-escaped.
- **Dimension**: `from` `[x,y]`, `to` `[x,y]`, `offset` (perpendicular distance from the measured line to the dimension line; sign picks side), optional `textOverride`. Renders extension lines, a dimension line with 45° ticks, and real-unit text (auto-formatted from `unit`, or `textOverride`). **Unit split, by design:** `offset` is in **model units** (it is a layout choice in the drawing's own space — where to park the dim line), while the tick size and text height are in **paper-mm** (they must read consistently regardless of scale). This split is intentional, not an inconsistency.
- **GridLine**: `label` (e.g. `"A"`, `"3"`), `from` `[x,y]`, `to` `[x,y]`, `bubbleEnds` (`start`|`end`|`both`). Rendered dash-dot with a labelled circle bubble at the chosen end(s).

### Site scale — `SiteSpec`
`render_site_plan` covers the whole exterior range, from an urban figure-ground down to a **detailed residential plot plan** (house footprint + its grounds). All exterior/outdoor detail lives here; `FloorPlanSpec` stays interior-only.

- **Building**: `id`, `footprint` (polygon), optional `label`, `floors`/`height` (annotation only), `style` (default: figure-ground **poché** — solid fill, heavy outline; overridable via `style.fill`/`style.hatch`).
- **Parcel** (was Block): `id`, `polygon`, optional `zone`, `style` (default: **dash-dot property/lot line**, no fill).
- **Road**: `id`, `path` (centerline), `width`, optional `type` (`arterial`|`local`|`pedestrian`), `style`. Offset (Clipper) → carriageway; roads offset→**union** so intersections merge (see Approach); optional dash-dot centerline.
- **PavedArea** (hardscape): `id`, `polygon`, `surface` (`concrete`|`asphalt`|`pavers`|`gravel`|`patio`|`deck`|`driveway`|`sidewalk`), optional `markings`, `style`. One entity covers **sidewalks, driveways, parking, patios, plazas, porches/decks** — each surface maps to a material hatch (`deck` → parallel board lines, `pavers` → grid, `gravel` → stipple, etc.).
  - **`markings`** (micro-schema, pinned): an array of **polylines**, each `{ path: [[x,y], …] }` with ≥2 points, rendered as **fine open lines, no fill** (`fine` lineweight, ink/accent color) — parking-stall striping, painted lot lines, crosswalk bars. This reuses the `path` convention of Wall/Road/Barrier, so no new geometry primitive: a straight stripe is a 2-point path, a U-shaped stall or crosswalk ladder is more points. The spec author (LLM) computes stall positions; the server only strokes them — consistent with dimensions/grid being spec-driven, not inferred.
- **Water**: `id`, `polygon`, optional `waterType` (`pool`|`pond`|`fountain`), `style` (default: light-blue fill / water hatch, heavy outline) — pools, ponds, water features.
- **GreenSpace** (soft landscape): `id`, `polygon`, `landscapeType` (`lawn`|`garden`|`planting`|`park`|`meadow`), `style`. `landscapeType` picks the fill/hatch — `lawn` = fine stipple, `garden`/`planting` = denser dot/blob texture, `park` = light fill. Covers lawns, garden beds, flower beds, backyards, planting areas.
- **Barrier** (linear boundary): `id`, `path`, `barrierType` (`fence`|`wall`|`hedge`|`gate`), `style` — property fences, garden/retaining walls, hedges, gates; each maps to a line symbol (fence = line with periodic posts, wall = thin solid, hedge = scalloped/green, gate = broken line).
- **Tree**: `id`, `position` `[x,y]`, `radius`, optional `species`/`style` — a standard circle-with-texture planting symbol.

Note: exterior features earlier flagged as possibly-missing (garden, lawn, pool, porch/deck, driveway, backyard, fences) are **all covered here** by `GreenSpace` (lawn/garden/backyard), `Water` (pool), `PavedArea` (porch/deck/driveway/patio/sidewalk/parking), and `Barrier` (fences/walls/hedges/gates) — they were never meant for the interior `FloorPlanSpec`.

### Building scale — `FloorPlanSpec`
- **Floor**: `id`, `level` (int; ground = 0; output ordering/naming), `outline` (polygon; fill-only slab), `label`, arrays: `rooms`, `walls`, `openings`, `dimensions`, `gridLines`.
- **Room**: `id`, `polygon`, `roomType` (`bedroom`|`kitchen`|`bathroom`|`living`|`hallway`|`circulation`|`other`), optional `label` (name; auto-appends computed **area** in `unit²` unless suppressed), `style` (**per-element `fill` highlight applies here**). **Decision — rooms are authored to the interior wall face, not wall centerlines.** This makes the computed area **honest usable floor area** (centerline area would overstate it by roughly half a wall thickness around the perimeter), and it decouples `Room` from `Wall` geometry (no dependency on wall thickness). It is also geometrically consistent: a wall centerline offset by half its thickness lands exactly on the room's inner-face edge, so room fill meets wall poché with no gap, and the `A-FLOR` layer sits under `A-WALL` regardless. The spec author places both (the room polygon and the wall centerlines); the server does not derive one from the other in v1.
- **Wall**: `id`, `path` (centerline), `thickness`, optional `material` (→ hatch) and `style`. Offset (Clipper, miter joins) to a band, then **unioned with the floor's other walls** into one cut-wall poché polygon (heavy outline + poché/material fill) — see the junction pipeline in Approach; walls are never stroked individually.
- **Opening**: `id`, `wallId`, `positionAlongWall` (0–1), `width`, `type` (`door`|`window`). For doors, two fields fully specify the swing (a single value can't — it needs ~2 bits): **`hinge`** (`start`|`end` — which jamb the hinge is on, along the wall's start→end direction) and **`swingSide`** (`left`|`right` — which side of the wall the leaf swings, relative to walking start→end). Cut from the wall polygon (Clipper `Difference`, after the wall union); door → leaf line (hinge→closed jamb) + 90° swing arc (centered on the hinge, sweeping to the `swingSide`); window → 2–3 parallel glazing lines spanning the gap **within the wall thickness** (not a bare gap).

Relationships: root specs hold flat sibling arrays; spatial containment is implicit from geometry. `Opening.wallId` must reference a `Wall` in the same `Floor` (validated — see Safeguards).

## A — Approach

- **Runtime & validation**: TypeScript/Node, MCP TypeScript SDK, **Zod** as the single source of truth for both root schemas (`z.infer`), enforced at each tool boundary. No unvalidated data reaches geometry/render code.
- **Geometry engine — Clipper + flatten-js (Turf.js is dropped)**. Turf is geospatial (spherical); its `buffer` is geodesic regardless of the `units` option, which is the root cause of the v1 buffer bug. This project is pure planar CAD geometry, so:
  - **`js-angusj-clipper`** (WASM port of Angus Johnson's Clipper — the industry-standard planar offsetting/clipping engine) does **offsetting** (`offsetToPaths`) and **boolean ops** (`clipToPaths`). Clipper requires **integer coordinates**, so `geometry/clipper.ts` wraps every call with a fixed precision multiplier (e.g. ×10⁴): scale model floats → int, run Clipper, scale back. The WASM instance is initialized **once at server startup** (`loadNativeClipperLibInstanceAsync`, async); geometry functions receive the ready instance and are otherwise synchronous and pure. WASM is bundled — no network, and determinism holds (fixed precision, fixed algorithm).
    - **Offsetting a centerline** (wall or road) is an **open polyline → closed band**: `offsetToPaths({ delta: thickness/2, joinType: Miter, endType: OpenButt })`. (`endType: ClosedPolygon` is for insetting/outsetting an already-closed ring, e.g. shrinking a room — *not* for centerlines, and would not produce a band.)
    - **Wall/road junction pipeline (critical — this is where v1's "outline-over-outline at intersections" artifact came from):** offset every wall centerline of a floor into its own band, then **`Union` all bands into one merged poché polygon**, *then* `Difference` the opening cutters from that union, *then* stroke the single resulting boundary. Unioning before stroking means interior edges at L/T junctions disappear — the heavy outline traces only the true outer/inner faces of the connected wall system, never the seams between abutting walls. Roads use the same offset→union pipeline so carriageways merge at intersections instead of one road's outline painting over another's. Cut openings **after** the union, never per-wall.
    - **Figure-ground / other closed rings**: `Union` overlapping building footprints; inset a room to its wall face with a negative-`delta` `ClosedPolygon` offset if ever needed (v1 keeps rooms author-supplied — see Entities).
  - **`@flatten-js/core`** provides analytic primitives — points, segments, arcs, affine `Matrix` transforms, centroid, point-along-path, perpendiculars — used for door swing arcs, dimension geometry, label placement, north-arrow/scale-bar construction, and bbox.
- **Coordinate & scale model**: model units = SVG user units = the spec's real `unit`; the `viewBox` is the padded world-space bbox (`minX minY W H`, no per-coordinate rescale — carried over from the v1 fix). **All annotation is authored in paper-mm and converted to model units** by `geometry/scale.ts` via `modelPerPaperMm = scaleDenominator / mmPerUnit`. So a `heavy` = 0.5 mm line at 1:100 with `unit: m` becomes `0.5 × 100 / 1000 = 0.05 m` of stroke width. This one conversion drives every line weight, text height, tick size, bubble radius, and the scale-bar geometry — nothing is a hardcoded pixel value.
- **Theme & line system** (`render/theme.ts`): a theme is a palette (`background`, `ink`, `pochéFill`, `hatchInk`, `accent`) plus the lineweight-role → paper-mm table and the linetype → `stroke-dasharray` table (dash lengths also in paper-mm → model units). `blueprint` = blue ground / near-white ink; `whiteprint` = white ground / near-black ink. A per-element `style.fill`/`style.stroke` **overrides** the theme for that element (the highlight feature) — validated to a safe color token first.
- **Poché & hatching** (`render/defs.ts`): each material maps to an SVG `<pattern>` in `<defs>` (concrete = stipple + triangles, brick/masonry = 45° lines, insulation = batting, earth = dense 45°, etc.); pattern tile sizes are in paper-mm → model units so hatch density is scale-correct. Patterns use **`patternUnits="userSpaceOnUse"`** (not `objectBoundingBox`) so hatching is scale-correct and continuous across adjacent elements rather than restarting per shape. Walls/buildings reference the pattern as `fill`, or a solid poché color, or a per-element `fill` override.
- **Rendering** = structured SVG string building (no headless browser, no canvas lib — output must stay deterministic, inspectable, testable). Organized, not ad-hoc:
  - **Deterministic number formatting**: Clipper is exact on integer input, but scaling back to floats and trig for arcs/dimensions produce values like `0.05000000000001`. Every coordinate/length is emitted through **one fixed formatter** (`render/primitives.ts`: round to a fixed decimal count — e.g. 4 — and strip trailing zeros) so "byte-identical SVG for identical spec" actually holds. No raw float is ever interpolated into markup.
  - **Text metrics without a font dependency**: SVG offers no measurement API and there is no font-metrics package. **Decision:** all annotation/label/title-block text uses a **monospace font stack**, and text width is computed as `charCount × fontSizeModel × ADVANCE_RATIO` (fixed `ADVANCE_RATIO ≈ 0.6`, the monospace advance-to-em ratio). Room-tag boxes, grid bubbles, and title-block field boxes are sized from this estimate plus a paper-mm padding. Monospace makes the estimate exact enough that boxes never clip, and keeps sizing dependency-free and deterministic.
  - `<defs>` holds hatch `<pattern>`s and reusable `<marker>`s (dimension ticks, arrowheads, north point).
  - Output is grouped into **NCS/AIA-inspired `<g>` layers** (floor: `A-FLOR`, `A-WALL`, `A-GLAZ`, `A-DOOR`, `A-ANNO-DIMS`, `A-ANNO-TEXT`, `S-GRID`; site: `V-PROP` parcels, `C-ROAD` roads, `L-HARD` hardscape/paving, `L-WATR` water, `L-PLNT` soft landscape + trees, `L-SITE` barriers, `A-BLDG` buildings, plus the shared `A-ANNO-*`). Layer order **is** the painter's-algorithm draw order, so professional layering and correct occlusion are the same mechanism — e.g. soft landscape and hardscape render beneath building poché, `A-FLOR` beneath `A-WALL`.
  - Sheet assembly (`render/sheet.ts`): compute drawing bbox → add paper-mm margins for border + title block → place the drawing, then the sheet border, title block, north arrow, and scale bar in the margin, all in the single model-unit space. **This is a proportional sheet, not a fixed paper size** — because everything lives in one model-unit space under a world-space viewBox, the border/title block/scale bar scale with the content rather than snapping to a real A1/A3 sheet. That is the right, simpler choice for on-screen SVG; true fixed-paper layout (choose A-series sheet, fit drawing to it at the named scale) is a deliberate later addition, noted in out-of-scope.
- **Shared core across scales**: Room/Building/Parcel/GreenSpace are all "polygon + style"; Wall/Road are "offset centerline + style". Geometry and the base render emitters are written against generic `PolygonEntity` / `LinearEntity` shapes, not entity names, so both tools share one geometry/render core; only entity-specific concerns differ (figure-ground poché vs room fill vs road carriageway; the wall **Opening** primitive; site trees).
- **Multi-floor**: each `Floor` → its own independent SVG sheet keyed by `level`; `render_floor_plan` returns one SVG per floor. No cross-floor/stacked/3D view.

## O — Operations

**Execution loop, per numbered step**: write the step's tests first (from its stated assertions) → confirm red → implement the minimum to pass → run the **full** suite → fix until green → only then advance. ## N — Norms

- **Test-first** per the Operations loop; full suite green before advancing.
- **TypeScript `strict: true`, no `any`.** Zod schemas are the single source of types (`z.infer`), never hand-duplicated.
- **Annotation sizing is authored in paper-mm and converted via the declared scale — never hardcoded pixel/user-unit constants.** A drawing at any scale must read correctly.
- Geometry (post-Clipper-init) and render functions are **pure** — input → output, no I/O, no input mutation. The Clipper WASM instance is initialized once and passed in; it is the only stateful dependency.
- Output is **layered**: every element is emitted inside its NCS-ish `<g>` layer; layer order is the single source of draw order.
- Tool-layer errors (validation, geometry) return **MCP tool errors** with a descriptive message — never an uncaught exception/stack trace to the client.
- **No network calls** anywhere (WASM is bundled). **Deterministic**: identical spec → byte-identical SVG — guaranteed by (a) the fixed Clipper precision multiplier, (b) **every emitted number passing through the single fixed formatter** (round to a fixed decimal count), (c) stable iteration order, and (d) `date`/title-block fields being spec-driven, never `Date.now()`.
- **Connected linework is unioned before stroking** (walls per floor, roads per site): offset → union → cut openings → stroke once. Never stroke individually-offset abutting bands — that re-introduces the interior-seam artifact.

## S — Safeguards

- All numeric fields (coordinates, widths, thicknesses, offsets, radii) validated finite and within sane bounds; reject NaN/Infinity/absurd magnitudes before geometry.
- **Clipper integer-overflow guard**: after applying the precision multiplier, coordinates must stay within Clipper's safe integer range — bound coordinate magnitude in the schema so `coord × precision` cannot overflow.
- **`unit` ∈ enum; `scale` matches `1:N`** with N in a sane range (reject `1:0`, negative, or absurd denominators).
- **Per-element `fill`/`stroke` must be a safe color token** — `#rgb`/`#rrggbb` or a fixed named-color allowlist — validated before it is ever interpolated into SVG. This closes the style/attribute-injection vector opened by making fill user-supplied. Every user string (`label.text`, room/floor labels, title-block fields) is XML-escaped.
- **All enum-like fields** — `material`, `roomType`, `zone`, `surface`, `landscapeType`, `barrierType`, `waterType`, `hinge`, `swingSide`, `linetype`, `lineweight`, `theme` — validated against their enums; unknown → tool error (or a documented safe fallback for `material`/`surface` → solid poché).
- **`Opening.wallId` must reference a `Wall` in the same `Floor`**, and `positionAlongWall` ∈ [0,1] — reject before geometry.
- **Entity count caps** (bound render cost/output size), conservative defaults: site — max 500 buildings / 200 roads / 200 paved areas (each ≤ 200 `markings` polylines of ≤ 100 points) / 100 water / 200 green spaces / 200 barriers / 500 trees; floor — max 100 floors, 100 rooms, 200 walls, 200 openings, 200 dimensions, 100 grid lines per floor.
- **File writes** only inside the server-configured allowed output directory (exact-match or `path.sep`-bounded prefix; reject `..` and prefix-lookalikes — carried from the v1 `outputPath.ts` fix).
- **Reject specs whose padded world extent exceeds a sane maximum** in either dimension (prevents pathological/huge SVG output).
